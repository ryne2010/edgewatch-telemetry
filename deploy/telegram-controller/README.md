# Telegram fleet controller deployment

This directory contains the non-secret controller configuration template and a
hardened systemd unit. The controller runs on one trusted, always-on Linux host;
it does not run on each Raspberry Pi.

## Files and ownership

Create the service account and directories before installing the unit:

```bash
sudo adduser --system --group --home /var/lib/edgewatch-controller edgewatch-controller
sudo install -d -o edgewatch-controller -g edgewatch-controller -m 0700 /var/lib/edgewatch-controller
sudo install -d -o root -g edgewatch-controller -m 0750 /etc/edgewatch-controller
```

Install these files under `/etc/edgewatch-controller`:

- `controller.yaml`: mode `0640`, owned by `root:edgewatch-controller`;
- `control_bot_token`: mode `0600`, owned by `edgewatch-controller`;
- `controller_device_ed25519`: mode `0600`, owned by `edgewatch-controller`;
- `spacebridge_rsa`, when used: mode `0600`, owned by `edgewatch-controller`;
- `known_hosts`: mode `0644`, with a pinned entry for every device alias and
  `[tunnel.hologram.io]:999` when Spacebridge is used;
- `releases.json`: mode `0644`, generated by the signed-release workflow.

Install the reviewed application at `/opt/edgewatch-controller/app`, create its
virtual environment, and install the agent requirements. The controller uses
the existing `requests` and `PyYAML` dependencies; no Telegram SDK is required.

```bash
cd /opt/edgewatch-controller/app
python3 -m venv .venv
.venv/bin/pip install --requirement agent/requirements.txt
sudo install -m 0644 deploy/telegram-controller/edgewatch-telegram-controller.service \
  /etc/systemd/system/edgewatch-telegram-controller.service
sudo systemctl daemon-reload
sudo systemctl enable --now edgewatch-telegram-controller
```

Before enabling field dispatch, enable secure device tunneling for each SIM in
Hologram and upload the public half of `spacebridge_rsa`. Hologram Spacebridge
uses outer SSH port `999`; each inventory `host` is the SIM's `linkNNNNNN`
profile identifier.

See `docs/RUNBOOKS/TELEGRAM_FLEET_CONTROL.md` for configuration, command policy,
home-to-field migration, OTA rollout, and recovery procedures.

Fleet mutations are previewed in full and require confirmation. The example
uses four concurrent device dispatches; tune `controller.fleet_dispatch_concurrency`
between 1 and 32 for the controller host and cellular fleet size.
Telegram update polling and reply delivery stay responsive while a separate
durable worker claims queued commands, dispatches bounded waves, and recovers
expired leases after restart. `controller.accepted_poll_interval_s` controls the
durable recheck interval for sample/sync requests accepted by a device but not
yet completed; keep it long enough to avoid repeated Spacebridge sessions.
